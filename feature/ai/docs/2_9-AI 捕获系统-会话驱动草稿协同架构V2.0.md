# AI捕获系统-会话驱动草稿协同架构 V2.0

## 1. 架构结论

- AI 角色从 **“流程决策者”降**级为 **“候选提议生成器”**。
- 客户端独占状态机、冲突决策、发布门禁三项权力。

## 2. 分层职责

### 2.1 AI 层（不可信输入源）

- 仅输出 `proposals.patches`、`proposals.clarify`、`signals`、`message`、`suggestions`。
- 不输出最终 `intent`、不控制状态迁移、不触发发布。

### 2.2 客户端编排层（唯一权威）

- 维护 `draft.version` 与会话轮次 `turn_id`。
- 执行 JSON Patch 安全校验、冲突处理、字段锁校验、回滚。
- 根据草稿完整度和本地规则推进状态：`EMPTY -> COLLECTING -> REVIEW -> READY -> PUBLISHED`。

### 2.3 Tool/CardEngine 层（执行层）

- 负责最终字段规范化、持久化与发布。
- 发布前必须通过本地 `prePublishCheck`，与 AI 建议解耦。

## 3. 协同协议

说明：

- 本节给出 V2 的完整请求/响应结构视图。
- “最小必填”指协议运行所需的最低字段集合，不代表能力被简化。
- 详细字段类型与约束以 `2_10-AI 捕获系统-会话协同协议JSON-SchemaV2.0.md` 为准。

### 3.1 请求结构（AiCaptureRequestV2）

- 完整结构：
- `protocol(version)`
- `session(id, turn_id)`
- `draft(version, data)`
- `constraints(required_fields, locked_fields, field_rules, conflict_policy)`
- `input(text, attachments)`
- `context(short_history, active_fields, language, key_facts)`
- 最小必填：
- `protocol.version`
- `session.id`
- `session.turn_id`
- `draft.version`
- `draft.data`
- `constraints.required_fields`
- `constraints.locked_fields`
- `constraints.field_rules`
- `constraints.conflict_policy`
- `input.text`
- `input.attachments`
- `context.short_history`
- `context.active_fields`
- `context.language`

### 3.2 响应结构（AiCaptureResponseV2）

- 完整结构：
- `proposals.patches`（**RFC 6902 JSON Patch**）
- `proposals.clarify`（结构化追问）
- `signals.publish_ready`
- `signals.needs_clarification`
- `message`（用户反馈文案）
- 最小必填：
- `proposals.patches`
- `proposals.clarify`
- `signals.publish_ready`
- `signals.needs_clarification`
- `message`

## 4. 一致性与恢复策略

- 版本一致性：仅接受 `base draft.version` 对齐的 patch，不对齐必须 rebase。
- 幂等策略：
- `add` 去重（对 tags/media 等集合字段）。
- `remove` 对缺失目标忽略不报错。
- 安全策略：
- 路径白名单限制。
- `locked_fields` 强约束。
- 失败恢复：
- patch 校验失败时只丢弃 patch，不中断会话。
- AI 不可用时进入纯手动编辑链路，系统继续可用。

## 5. Token 与性能策略

- 不再每轮传完整 `field_specs`，改为 `constraints + active_fields`。
- `context.short_history` + `context.key_facts` 双轨上下文，减少长文本漂移。
- 控制响应复杂度，避免解释性冗余字段，减少模型编造理由的空间。

## 6. 系统提示词与人设配置（V2）

### 6.1 是否需要补齐？

- 需要。V2 虽然弱化了 AI 决策权，但仍依赖 AI 生成 `proposals`，提示词和人设决定提议质量、语气一致性与澄清效率。
- 目标不是让 AI 决策流程，而是让 AI 在固定边界内稳定地产生高质量候选。

### 6.2 运行时上下文（每轮请求都传）

```json
{
  "runtime_context": {
    "now": "2026-04-17T10:00:00+08:00",
    "timezone": "Asia/Shanghai",
    "location": {
      "name": "Shanghai",
      "lat": 31.2304,
      "lng": 121.4737,
      "source": "gps|manual|inferred"
    },
    "language_preference": "zh-CN",
    "device_locale": "zh-CN",
    "privacy_mode": "strict|normal",
    "tool_capability": [
      "add_media",
      "update_title",
      "update_tags"
    ]
  }
}
```

约束：

- 时间与地点只用于理解和措辞，不可绕过本地权限策略。
- 相对时间词（今天/明天）必须由客户端映射为绝对时间后再入库。

### 6.3 V2 系统提示词模板（建议基线）

```text
你是“结构化捕获助手”，只生成 AiCaptureResponseV2。

优先级：
1) 先补 active_fields，再补 required_fields 中仍缺失的字段。
2) 能从输入安全提炼的 title、tags、summary，直接输出 patches。
3) 只有缺少无法可靠推断的关键信息时才输出 clarify。
4) 非阻塞增强放到 suggestions。

硬约束：
- 只输出一个 JSON 对象，不要解释、不要回显请求、不要额外字段。
- 顶层只允许 proposals、signals、message、suggestions。
- 不生成超出 constraints 和 active_fields 的字段修改。
- 不修改 locked_fields 对应路径。
- 仅修改 /title、/summary、/tags、/extra/*；媒体相关动作只通过 suggestions 表达，不要输出 /media patch。
- /title、/summary 的 value 必须是字符串；/tags、/tags/- 的 value 必须是字符串或字符串数组。
- message 只能描述真实 patch / clarify / suggestions 结果。
- 仅 suggest_tags、set_location、set_capture_type 允许 payload；其余 suggestion 不要携带 payload。
```

### 6.4 人设与预期配置（persona_profile）

```json
{
  "persona_profile": {
    "name": "Milo",
    "role": "结构化捕获助理",
    "tone": "专业、简洁、友好",
    "verbosity": "short|normal",
    "emoji_policy": "none|limited",
    "safety_style": "仅做信息整理，不做高风险结论"
  }
}
```

建议：

- 需要人设。不是为了拟人，而是为了稳定回复风格、降低文案抖动。
- 默认使用中性人设，不在 prompt 中硬编码性别设定；若产品要角色风格，走配置中心下发。

### 6.5 可从旧方案借鉴但已按 V2 重构的内容

- `runtime_context`：时间/时区/位置/语言上下文。
- `system_prompt_profile`：统一提示词入口，但输出约束改为 V2 的 proposals-only。
- `persona_profile`：语气和风格配置，避免多模型切换导致回复风格漂移。

## 7. 落地检查清单

- 客户端实现 **JSON Patch** 解析与安全白名单。
- 客户端实现 `draft.version` 并发校验与 rebase。
- 客户端实现冲突策略 `user_wins/merge/append/ai_wins`。
- 状态机完全脱离 AI 输出，仅消费本地规则与用户行为。（已经实现）
- 发布门禁只走本地校验链路。
