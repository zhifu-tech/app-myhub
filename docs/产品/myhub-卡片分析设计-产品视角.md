# 卡片分析设计 — 产品视角（全新框架）

> **文档定位**：从产品经理视角重新定义「卡片分析」——不按输入类型分类，而是从**用户为什么存、存了怎么用**出发，推导出分析维度、分析产出与卡片类型体系。  
> **关联**：[myhub-产品思考与定位文档_v0.1.md](myhub-产品思考与定位文档_v0.1.md)、[myhub-卡片与卡集的设计思路.md](myhub-卡片与卡集的设计思路.md)。

---

## 一、为什么要做「卡片分析」？

### 1.1 产品要回答的问题

MyHub 的核心承诺是：**让已经收藏的内容，真正用回来。**

因此不能只做「存下来」，还要在存的时候和存之后回答以下问题：

| 问题          | 谁在问    | 分析要支撑什么           |
|-------------|--------|-------------------|
| 这是什么？       | 系统、用户  | 展示方式、筛选、搜索        |
| 用户当时为什么存？   | 系统（推断） | 推荐归入哪个卡集、何时提醒复看   |
| 之后会怎么用？     | 产品设计   | 复看节奏、再传播形式、是否可作模板 |
| 和别的卡片有什么关系？ | 系统     | 标签、卡集建议、关联推荐      |

**卡片分析**：在用户完成「收集」时，对内容做一次结构化分析，产出主类型、来源形态、metadata、标签等；用户编辑或能力升级后，对卡片做必做的再分析。分析产出的结构化结果用于支撑卡片的**展示、组织、复看与再传播**。

### 1.2 分析服务于什么

- **体验**：用对的形态展示（该用代码高亮就别当普通段落）。
- **发现**：能按「类型 / 标签 / 用途」筛选和搜到。
- **复用**：复看时给对的信息密度（摘要 vs 全文）、再分享时给对的形式（链接 / 摘抄图 / 代码片段）。
- **扩展**：后续做智能提醒（「这类内容你通常一周后会复看」）、卡集建议（「和这几张卡一起看」）时，有可用的结构化信号。

## 二、全新视角：从「用户结果」倒推分析维度

**不按「用户输入是什么（URL/文本/图/视频）」分类，而按「用户存了之后要得到什么结果」来设计。**

### 2.1 用户存内容的三种结果诉求

| 诉求             | 含义                       | 典型场景               |
|----------------|--------------------------|--------------------|
| **我要再看到它**     | 内容本身有价值，需要复看、复习或随时调出     | 文章、视频、摘抄、教程链接、代码片段 |
| **我要照着做 / 执行** | 内容承载的是「待办」或「步骤」，存下来是为了去做 | 待办、清单、菜谱步骤、学习计划    |
| **我要拿它当素材**    | 存下来是为了再创作、再分享或当模板用       | 金句、代码模板、商品卡片、站点入口  |

同一份原始内容可能对应多种诉求（例如一篇教程既「再看到」又「照着做」）。**只选一个主诉求**作为卡片的「主类型」，其余用标签、卡集或 metadata 表达，以降低心智负担。

### 2.2 内容与外界的关系（来源形态）

用户存下来的东西，和「外部世界」的关系决定了：我们是**存指针**还是**存副本**，以及能否「回源」：

| 形态              | 含义                | 产品含义                                |
|-----------------|-------------------|-------------------------------------|
| **引用（Link）**    | 指向外部资源，内容在别处      | 存 URL + 摘要/封面；可跳转回源；可做可用性/更新检测（如站点） |
| **摘录（Extract）** | 从某处摘出一段，副本在 MyHub | 存正文/片段；不再依赖原链接；适合摘抄、代码片段、金句         |
| **自创（Own）**     | 用户自己写/录的，没有「原出处」  | 笔记、想法、待办、本地视频；完全归属用户                |

分析必须判断这张卡的来源形态是「引用」「摘录」还是「自创」，以便决定：是否展示来源与跳转、是否做链接健康检查、以及采用何种展示与版权策略。

### 2.3 内容载体（呈现形态）

用户「再看到它」时，最适合的呈现方式是什么？这决定**展示层**和**存储结构**，而不是决定「类型」本身：

| 载体    | 典型形态        | 产品侧需要                    |
|-------|-------------|--------------------------|
| 以文为主  | 段落、列表、代码、金句 | 排版、代码高亮、引用样式             |
| 以图为主  | 单图、截图、信息图   | 缩略图、大图查看、OCR             |
| 以视频为主 | 视频链接或上传     | 封面、时长、平台、播放              |
| 以链接为主 | 单链接、站点入口    | URL、标题、摘要、favicon、「站点」能力 |

同一张卡可以既有「文」又有「图」（例如文章带封面）。**载体**表示卡片具备哪些展示能力，多种载体可同时存在，不必互斥。

> OCR 即光学字符识别，从图中识别并提取文字，用于后续分析或检索）

## 三、卡片分析应产出什么（分析输出）

分析的目的是产出**可被使用的结构化结果**（主类型、来源形态、metadata、标签等），用于展示、筛选与复看。

### 3.1 第一层：主类型（Primary Type）— 仅按诉求定义

- **作用**：决定这张卡「主要是干什么用的」、默认筛选项、以及列表/详情里的**行为侧重**（复看 / 执行 / 当素材用）。
- **原则**：类型完全由「分析出的诉求」推导；类型少、互斥、规则清晰；展示形态由第二层「来源形态」+ 第三层「metadata / 载体」决定用哪类组件。

**类型集（仅由 §2.1 三种诉求得出）**：

| 类型               | 对应诉求       | 含义                 | 展示/行为侧重                                                                       |
|------------------|------------|--------------------|-------------------------------------------------------------------------------|
| **再看到（review）**  | 我要再看到它     | 存下来是为了复看、复习或随时调出   | 以「呈现内容、支持复看」为主；具体形态由来源形态 + metadata 决定（链接则跳转/摘要，视频则封面/播放，摘抄则正文/代码高亮，词条则释义/复习） |
| **执行（do）**       | 我要照着做 / 执行 | 存下来是为了去做、勾选、按步骤执行  | 可勾选、可排序、可提醒；清单/步骤式交互                                                          |
| **素材（material）** | 我要拿它当素材    | 存下来是为了再创作、再分享或当模板用 | 以「可被引用、可再发」为主；金句、模板、站点入口、商品卡等                                                 |

仅此三种类型。更细的筛选或展示差异由**来源形态**（Link / Extract / Own）和 **metadata**（如 contentType、是否有 URL、是否有视频）驱动，类型层规则单一：**类型 = 分析出的诉求**。

### 3.2 第二层：来源形态（Link / Extract / Own）

- **作用**：决定是否展示来源与「打开原链接」、是否做链接健康检查、是否启用站点能力。
- **产出**：来源形态取值（Link / Extract / Own）；若为引用则必填 URL，若为站点则必填站点 ID。用于详情页、列表副标题、运营/分析。

### 3.3 第三层：结构化元数据（Metadata）

- **作用**：支撑展示与筛选。
- **产出**：作者、出处、语言、时长、平台、站点名/favicon、代码语言等，按类型不同而不同，由分析管道与用户编辑共同填充。该层必须产出；各字段按是否适用分为必填与选填。

### 3.4 第四层：语义与意图（标签、建议卡集、复看建议）

- **作用**：标签用于筛选与发现；建议卡集降低「存完不知道放哪」的摩擦；复看建议支撑「智能提醒」。
- **产出**：标签列表、「建议加入的卡集」、「建议复看方式」（如「适合一周后复看」）。三者均需产出，以形成完整产品体验。

## 四、分析触发的时机与输入

- **主触发**：用户完成「收集」时（粘贴/上传/输入后点击保存或「用 AI 生成」），对当前内容做一次分析。输入可以是 URL、文本、图片、视频或其组合。
- **再分析**：用户编辑类型或内容后、或分析能力升级后，对已有卡片做再分析，用于补全标签、更新摘要等；再分析为完整体验的一部分，必须支持。

**输入形态不直接决定类型**。类型由分析出的诉求与用户选择共同决定：同一段文本可能被分析为「再看到」「执行」或「素材」，用户可在创建或编辑时修改类型；URL 同样先解析出诉求，再落为主类型。

---

## 五、类型推断逻辑（按诉求推断）

系统先**根据内容特征推断用户诉求**，再给出默认主类型；用户可在创建或编辑时修改类型。

### 5.1 从内容特征推断「诉求」

- 检测到**可执行结构**（清单、勾选项、步骤列表）→ 诉求为「照着做/执行」→ 类型 **执行（do）**。
- 检测到**金句/模板/站点入口/商品卡**等明显「用来再发、当素材」的形态 → 诉求为「拿它当素材」→ 类型 **素材（material）**。
- 其余（链接、视频、摘抄、代码片段、笔记、词条、长文、图片等）→ 诉求为「再看到它」→ 类型 **再看到（review）**。

同一输入可能对应多种类型（例如教程既可判为「再看到」也可判为「照着做」）。系统给出**默认诉求**，用户可在创建或编辑时切换为三种类型之一。

### 5.2 用户可覆盖

- 创建/编辑时，类型以 **Chips 或下拉** 展示三种选项（再看到 / 执行 / 素材），默认选中分析结果，用户可切换。
- 类型一旦改变，展示与 metadata 表单随之切换（例如从「再看到」改为「执行」则出现勾选/步骤能力），分析产出的其他结果（标签、摘要、来源形态）可保留。

---

## 六、收集流程与分析管道

- **收集流程**：用户粘贴或上传内容（URL / 文本 / 图片 / 视频或组合）→ 系统分析并给出主类型、来源形态、metadata、标签 → 用户可修改类型与字段后保存。
- **分析管道**：根据内容特征推断用户诉求（再看到 / 执行 / 当素材），输出主类型，并输出来源形态、metadata、标签。输入形态（URL/文本/图/视频）只在管道内部用于分支逻辑，不作为用户可见的分类维度。
- **站点**：整站入口按诉求归入「再看到」（复访）或「素材」（对外展示）；站点相关能力（可用性、统计等）通过 metadata 承载。

## 七、总结：卡片分析的设计原则

| 原则          | 说明                                                              |
|-------------|-----------------------------------------------------------------|
| **诉求即类型**   | 主类型仅由「分析出的诉求」定义（再看到 / 执行 / 素材），规则单一。                            |
| **类型极简**    | 仅三种类型、互斥、对用户可解释；展示差异由来源形态 + metadata 驱动。                        |
| **分析多产**    | 分析产出主类型 + 来源形态 + metadata + 标签 + 建议卡集 + 复看建议（四层产出均必做，支撑完整产品体验）。 |
| **输入与类型解耦** | 同一输入可对应不同诉求，类型由分析结果与用户选择共同决定；输入形态只在分析管道内部使用，不作为用户可见的分类。         |
| **可解释**     | 用户能理解「为什么系统建议是再看到/执行/素材」，必要时在 UI 上轻量说明。                         |
