## 1. 问题背景

### 1.1 用户场景

MVP 阶段支持离线使用，默认不要求用户登录。用户可以直接使用应用功能，但需要一个稳定且可持久的唯一标识，用于：

- 行为统计与 MVP 验证
- 本地数据归属与隔离
- 后续同步或登录升级的平滑过渡

### 1.2 问题根因

没有登录体系时缺少用户主键，导致无法进行用户级统计与数据归属。  
同时产品强调离线优先，不能强依赖网络或服务端注册流程。

### 1.3 影响范围

- 客户端身份生成与持久化
- 本地数据库的用户主键设计
- 数据统计上报的匿名标识
- 未来登录/同步的迁移兼容

---

## 2. 设计目标

### 2.1 功能目标

- ✅ 无需登录即可生成唯一身份
- ✅ 在离线场景可用且稳定
- ✅ 支持本地数据归属与隔离
- ✅ 为后续账号体系预留升级路径

### 2.2 非功能目标

- 隐私合规：不采集硬件级标识（IMEI/IDFA）
- 跨平台：Android/iOS/Desktop/Web 均可实现
- 稳定性：卸载重装可视为新身份

---

## 3. 技术调研

### 3.1 候选方案

#### 方案 A：设备硬件标识（IMEI/IDFA/AAID）

- 优势：稳定、不易变
- 劣势：隐私风险高、平台限制严格
- 适用场景：合规要求低且强制登录的应用（不适合 MVP）

#### 方案 B：安装级匿名 ID（UUID v4）

- 优势：隐私友好、离线可用、易实现
- 劣势：卸载重装会重置
- 适用场景：MVP、匿名场景、离线优先

#### 方案 C：服务端分配匿名账号

- 优势：可统一统计与服务端追踪
- 劣势：首次启动需网络，违背离线优先

### 3.2 方案对比

| 维度     | 方案 A 设备标识 | 方案 B 安装级 UUID | 方案 C 服务端匿名 |
|--------|-----------|---------------|------------|
| 离线可用   | ✅         | ✅             | ❌          |
| 隐私合规   | ❌         | ✅             | ✅          |
| 跨平台一致性 | ❌         | ✅             | ✅          |
| 实现复杂度  | 中         | 低             | 中          |
| 升级可扩展性 | 中         | ✅             | ✅          |

### 3.3 推荐方案

**推荐方案 B：安装级匿名 ID（UUID v4）**。  
理由：符合离线优先与隐私合规要求，跨平台一致性好，且可在后续同步或登录时扩展绑定逻辑。

## 4. 架构设计

### 4.1 整体架构

```text
App 启动
  └─ 读取本地 user 表（当前用户）
       ├─ 存在 -> 直接使用 userId
       └─ 不存在 -> 读取本地 installId
             ├─ 存在 -> 作为 userId 写入 user 表
             └─ 不存在 -> 生成 UUID v4 -> 持久化 -> 写入 user 表
```

### 4.2 核心组件

- **Bootstrap**
    - 生成 UUID v4 作为匿名 userId
    - 写入本地 user 表
- **LocalUserRepository**
    - 读取当前用户并提供给业务层
- **Analytics/Sync**（可选）
    - 使用匿名 userId 作为关联键

### 4.3 数据流

1. 启动时读取本地 user 表，若存在则直接使用
2. 未存在则读取本地 installId
3. installId 不存在则生成 UUID v4 并持久化
4. 写入本地 user 表（anonymous）
5. 业务层统一使用 userId 进行数据归属与统计

## 7. 风险评估

### 7.1 技术风险

- **卸载重装导致身份变化** → 可接受，符合隐私合规与 MVP 目标
- **Web 存储不稳定** → 增加本地备份或服务端兜底
- **匿名用户与登录用户合并策略** → 后续版本设计

### 7.2 边界条件

- 不要求登录、默认不进行网络注册
- 匿名 userId 仅用于本地归属与统计
- 不保证跨设备一致（除非未来绑定账号）
