# MyHub 架构设计文档规范及评审规则

**本规则详细定义了 MyHub 基础设施层（Infra）的架构设计文档结构、内容标准与评审要求**。其核心目的是确保所有基础设施相关技术方案文档具备**清晰的结构**、**一致的表达**和**可评审性**，从而提升架构决策的透明度和可追溯性。**规则内容包括但不限于：文档需包含的头部元信息、目录结构、核心章节（如需求背景、设计目标、技术对比、实现细节、实施计划等），以及具体的内容检查清单。**所有 Infra 层（如数据存储、依赖注入、日志、数据库等）相关的重要架构方案和技术 RFC，均应严格遵循本规则撰写和提交，以保障架构方案的可理解性与后续维护扩展的高效性。

- **版本编号：v1.0**
- 面向的使用者：`AI Copilot`

## 📋 适用范围

本规则适用于所有：

- 架构设计文档
- 技术方案文档
- RFC(Request For Comments, 征求意见稿) 文档

## 1. 文档结构检查清单

### 1.1 文档头部信息（必需）

每个架构设计文档必须包含以下头部信息：

- ✅ **文档标题**：清晰描述文档主题
- ✅ **文档版本**：版本号（如 v1.0，bugfix 使用 v1.0.1, v1.0.2 等）
- ✅ **文档类型**：技术方案设计文档 / RFC / 架构设计
- ✅ **创建日期**：YYYY-MM-DD 格式
- ✅ **最后更新**：YYYY-MM-DD 格式
- ✅ **作者**：作者或团队名称
- ✅ **评审状态**：🟢 通过 / 🟡 待评审 / 🔴 需修改
- ✅ **方案状态**：🔒 已锁定 / 📝 进行中 / ⏸️ 暂停
- ✅ **修改历史**（如已修改）：记录每次修改的版本、日期、修改内容和原因

#### 评审状态定义

评审状态用于标识文档的评审进度，必须在文档头部明确标注：

- 🟢 **通过**：文档已通过评审，可以进入实施阶段
  - 适用于：主版本号（Major）和次版本号（Minor）更新
  - 说明：评审者已确认方案可行，可以开始实施或已锁定
  
- 🟡 **待评审**：文档正在等待评审或评审进行中
  - 适用于：新创建的文档或提交评审后的文档
  - 说明：文档已完成初稿，等待评审者审查
  
- 🔴 **需修改**：文档评审后需要修改
  - 适用于：评审者提出修改意见后的文档
  - 说明：文档需要根据评审反馈进行修改，修改后应更新为"待评审"状态

#### 方案状态定义

方案状态用于标识方案的实施进度，必须在文档头部明确标注，并在实施计划章节中体现：

- 🔒 **已锁定**：方案设计已确定，不允许随意修改
  - 适用于：已通过评审并开始实施的方案
  - 说明：方案已冻结，如需修改需要提交设计变更申请
  - **在文档中的体现**：应在文档头部标注，并在实施计划中说明锁定日期和锁定原因
  
- 📝 **进行中**：方案设计正在进行中，可以修改
  - 适用于：正在编写或修改的文档
  - 说明：文档处于活跃状态，可以随时更新
  - **在文档中的体现**：应在文档头部标注，并在实施计划中说明当前进度和下一步计划
  
- ⏸️ **暂停**：方案设计暂时停止，保留当前状态
  - 适用于：因各种原因暂时停止的方案
  - 说明：方案暂时搁置，但保留当前设计状态
  - **在文档中的体现**：应在文档头部标注，并在实施计划中说明暂停原因和预计恢复时间

#### 状态在文档中的体现要求

为了便于查看文档的人了解进度，评审状态和方案状态应在以下位置体现：

1. **文档头部**（必需）：在文档头部信息中明确标注当前状态
2. **实施计划章节**（推荐）：在实施计划章节中说明当前进度，特别是方案状态的变化
3. **修改历史**（如适用）：如果状态发生变化，应在修改历史中记录状态变更
4. **文档目录前**（可选）：可以在文档目录前添加状态摘要，快速了解文档状态

### 1.1.1 文档命名规范（必需）

文档文件名必须包含版本信息，使用 `-infra-v` 后缀：

- ✅ **初始版本**：`[文档名称]-infra-v1.0.md`（如：`myhub-nav-infra-v1.0.md`）
- ✅ **Bugfix 版本**：`[文档名称]-infra-v1.0.1.md`、`[文档名称]-infra-v1.0.2.md` 等
- ✅ **重大版本**：`[文档名称]-infra-v2.0.md`、`[文档名称]-infra-v3.0.md` 等
- ✅ **命名规则**：
  - 使用小写字母和连字符（kebab-case）
  - 必须包含 `-infra-v` 后缀
  - 版本号格式：`v主版本号.次版本号.修订号`
  - 示例：`myhub-navigation-design-infra-v1.0.md`、`myhub-navigation-design-infra-v1.0.1.md`

#### 版本号含义说明

文档版本号遵循语义化版本规范（Semantic Versioning）：

- ✅ **主版本号（Major）**：重大更新，如架构升级、设计理念变更
  - 需要架构评审
  - 示例：`v1.0` → `v2.0`（架构升级）
- ✅ **次版本号（Minor）**：增加功能等不影响架构的改动
  - 需要技术评审
  - 示例：`v1.0` → `v1.1`（新增功能模块）
- ✅ **修订号（Patch）**：问题修复、文档错误修正、格式优化等
  - **不需要评审**，可直接修改
  - 示例：`v1.0` → `v1.0.1`（修复错误）

### 1.2 文档目录结构（必需）

文档必须包含以下核心章节：

#### 基础章节（必需）

1. ✅ **问题背景 / 动机**

   - 用户场景描述
   - 问题根因分析
   - 影响范围说明

2. ✅ **设计目标**

   - 功能目标（明确、可衡量）
   - 非功能目标（性能、可维护性、跨平台等）

3. ✅ **技术调研 / 方案对比**

   - 候选方案列表
   - 方案对比表格
   - 官方证据链接
   - 推荐方案及理由

4. ✅ **架构设计 / 方案设计**

   - 整体架构图
   - 核心组件设计
   - 数据流设计
   - 状态管理设计

5. ✅ **实现细节**

   - 关键 API 设计
   - 代码示例
   - 依赖配置
   - 平台特定实现

6. ✅ **实施计划**

   - 分阶段实施步骤
   - 里程碑定义
   - 时间估算

7. ✅ **风险评估**
   - 技术风险识别
   - 风险缓解措施
   - 边界条件说明

#### 扩展章节（按需）

- **测试策略**：单元测试、集成测试、平台测试
- **性能考虑**：性能指标、优化策略
- **迁移计划**：从旧方案迁移的步骤
- **附录**：相关文档链接、术语表、参考资料

## 2. 技术评审要点

### 2.1 KMP 跨平台考虑（必需检查）

对于涉及跨平台的方案，必须明确说明：

- ✅ **平台支持范围**：Android、iOS、Desktop、Web 支持情况
- ✅ **平台差异处理**：平台特定实现的位置和方式
- ✅ **expect/actual 机制**：如何使用平台抽象
- ✅ **平台测试策略**：如何在各平台验证功能

**检查问题**：

- [ ] 是否明确说明每个目标平台的支持情况？
- [ ] 是否识别了平台特定的实现需求？
- [ ] 是否提供了平台抽象的设计方案？
- [ ] 是否说明了平台测试的覆盖范围？

### 2.2 架构一致性检查（必需检查）

方案必须与现有架构保持一致：

- ✅ **模块组织**：是否符合现有模块结构（core、feature、component）
- ✅ **依赖关系**：依赖方向是否正确（UI → Domain → Data）
- ✅ **设计模式**：是否遵循 MVVM、Repository 等现有模式
- ✅ **依赖注入**：是否使用 Koin，配置是否正确

**检查问题**：

- [ ] 新模块是否遵循现有的模块命名和组织规范？
- [ ] 依赖关系是否符合分层架构原则？
- [ ] 是否复用了现有的 core 模块能力？
- [ ] DI 配置是否与现有模块一致？

### 2.3 状态管理设计（必需检查）

对于涉及状态管理的方案，必须明确：

- ✅ **状态定义**：UI State、业务状态、导航状态的划分
- ✅ **状态持有者**：ViewModel、State Holder 的选择
- ✅ **状态同步**：跨屏幕、跨模块的状态同步机制
- ✅ **状态持久化**：状态保存和恢复策略

**检查问题**：

- [ ] 是否明确区分了 UI 状态和业务状态？
- [ ] 状态持有者的生命周期是否合理？
- [ ] 是否需要跨模块状态共享？如何实现？
- [ ] 状态持久化策略是否考虑了平台差异？

### 2.4 导航设计（如涉及导航）

对于导航相关的方案，必须明确：

- ✅ **导航模型**：Navigation 3 / Compose Nav / 自定义
- ✅ **导航栈管理**：返回栈的创建、保存、恢复
- ✅ **平台返回处理**：系统返回按钮、浏览器后退等
- ✅ **深度链接**：Deep Link 支持情况

**检查问题**：

- [ ] 是否选择了合适的导航库？理由是否充分？
- [ ] 导航栈的生命周期管理是否清晰？
- [ ] 是否处理了平台特定的返回事件？
- [ ] Deep Link 支持是否完整？

### 2.5 数据层设计（如涉及数据）

对于数据相关的方案，必须明确：

- ✅ **数据源**：Local（SQLDelight）、Remote（Ktor Client）
- ✅ **数据模型**：Entity、DTO、UI Model 的转换
- ✅ **数据流**：Flow、StateFlow 的使用
- ✅ **缓存策略**：数据缓存和同步机制

**检查问题**：

- [ ] 是否遵循了现有的 Repository 模式？
- [ ] 数据模型转换是否清晰？
- [ ] 数据流是否考虑了错误处理？
- [ ] 缓存策略是否合理？

## 3. 代码质量检查

### 3.1 代码示例要求

文档中的代码示例必须：

- ✅ **完整性**：包含必要的 import、类型定义
- ✅ **可运行性**：代码示例应该可以直接使用或稍作修改即可运行
- ✅ **最佳实践**：遵循 Kotlin 和 Compose 最佳实践
- ✅ **平台兼容**：如果是跨平台代码，明确标注平台范围

**检查问题**：

- [ ] 代码示例是否包含必要的上下文？
- [ ] 代码示例是否可以直接使用？
- [ ] 是否遵循了 Kotlin 编码规范？
- [ ] 是否标注了平台特定的代码？

### 3.2 API 设计检查

- ✅ **API 命名**：遵循 Kotlin 命名规范，语义清晰
- ✅ **参数设计**：参数是否合理，是否支持默认值
- ✅ **返回值**：返回值类型是否明确，是否支持 Flow/StateFlow
- ✅ **错误处理**：异常处理机制是否完善

**检查问题**：

- [ ] API 命名是否清晰易懂？
- [ ] 参数设计是否合理？
- [ ] 错误处理是否完善？
- [ ] 是否考虑了向后兼容性？

## 4. 风险评估要求

### 4.1 技术风险识别（必需）

必须识别以下类型的风险：

- ✅ **技术选型风险**：新技术的成熟度、社区支持
- ✅ **平台兼容性风险**：跨平台实现的复杂度
- ✅ **性能风险**：性能瓶颈和优化需求
- ✅ **迁移风险**：从旧方案迁移的复杂度
- ✅ **维护风险**：长期维护的难度

**检查问题**：

- [ ] 是否识别了所有主要技术风险？
- [ ] 每个风险是否有对应的缓解措施？
- [ ] 风险等级是否合理评估？
- [ ] 是否有风险应对预案？

### 4.2 边界条件说明（必需）

必须明确说明方案的边界和限制：

- ✅ **功能边界**：方案解决什么问题，不解决什么问题
- ✅ **平台边界**：哪些平台完全支持，哪些平台部分支持
- ✅ **性能边界**：性能指标和限制
- ✅ **兼容性边界**：向后兼容性、API 兼容性

**检查问题**：

- [ ] 是否明确说明了方案的适用范围？
- [ ] 是否说明了不支持的场景？
- [ ] 平台支持情况是否准确？
- [ ] 兼容性要求是否明确？

## 5. 实施计划要求

### 5.1 分阶段实施（推荐）

实施计划应该分阶段进行：

- ✅ **阶段划分**：按功能模块或优先级划分阶段
- ✅ **里程碑定义**：每个阶段的明确产出
- ✅ **依赖关系**：阶段之间的依赖关系
- ✅ **时间估算**：每个阶段的时间估算

**检查问题**：

- [ ] 实施计划是否分阶段？
- [ ] 每个阶段的目标是否明确？
- [ ] 阶段依赖关系是否清晰？
- [ ] 时间估算是否合理？

### 5.2 回滚策略（如适用）

对于重大变更，应该提供回滚策略：

- ✅ **回滚条件**：什么情况下需要回滚
- ✅ **回滚步骤**：具体的回滚操作步骤
- ✅ **数据迁移**：回滚时的数据迁移策略

## 7. 评审流程

### 7.1 自检阶段

在提交评审前，作者应该：

1. ✅ 使用本规则进行自检
2. ✅ 填写文档完整性检查清单
3. ✅ 修复明显的错误和不一致
4. ✅ 确保所有链接有效

### 7.2 技术评审阶段

评审者应该：

1. ✅ 按照本规则逐项检查
2. ✅ 重点关注技术选型和架构设计
3. ✅ 检查平台兼容性和风险
4. ✅ 提供具体的修改建议

**评审要求说明**：

- ✅ **主版本号（Major）更新**：需要架构评审，重点关注架构变更、设计理念变更
- ✅ **次版本号（Minor）更新**：需要技术评审，重点关注功能扩展、设计补充
- ✅ **修订号（Patch）更新**：不需要评审，可直接修改

### 7.3 评审反馈处理

作者应该：

1. ✅ 记录所有评审反馈
2. ✅ 在文档中明确标注已修复的问题
3. ✅ 对于未采纳的建议，说明理由
4. ✅ 更新文档状态和版本号：
   - 修订号（Patch）：v1.0 → v1.0.1（不需要评审）
   - 次版本号（Minor）：v1.0 → v1.1（需要技术评审）
   - 主版本号（Major）：v1.0 → v2.0（需要架构评审）
5. ✅ 更新评审状态和方案状态：
   - 根据评审结果更新评审状态（🟢 通过 / 🟡 待评审 / 🔴 需修改）
   - 根据实施进度更新方案状态（🔒 已锁定 / 📝 进行中 / ⏸️ 暂停）
   - 在实施计划章节中说明状态变更和当前进度
6. ✅ 在修改历史中记录修改内容、日期和原因，如状态发生变更也应记录

## 9. 常见问题检查

### 9.1 技术选型常见问题

- ❌ **问题**：技术选型理由不充分

  - ✅ **解决**：提供官方文档链接、社区支持情况、实际使用案例

- ❌ **问题**：未考虑平台兼容性

  - ✅ **解决**：明确说明每个平台的支持情况，提供平台特定实现方案

- ❌ **问题**：未考虑性能影响
  - ✅ **解决**：提供性能测试数据，说明性能优化策略

### 9.2 架构设计常见问题

- ❌ **问题**：模块职责不清晰

  - ✅ **解决**：明确每个模块的职责边界，提供模块依赖图

- ❌ **问题**：状态管理混乱

  - ✅ **解决**：明确状态层次（UI State、业务状态、导航状态），说明状态同步机制

- ❌ **问题**：未考虑扩展性
  - ✅ **解决**：说明如何添加新功能，如何扩展现有功能

### 9.3 实施计划常见问题

- ❌ **问题**：实施计划过于粗略

  - ✅ **解决**：分阶段实施，每个阶段有明确的产出和时间估算

- ❌ **问题**：未考虑依赖关系

  - ✅ **解决**：明确阶段之间的依赖关系，提供依赖图

- ❌ **问题**：未考虑回滚策略
  - ✅ **解决**：对于重大变更，提供回滚策略和步骤

### 9.4 状态管理常见问题

- ❌ **问题**：评审状态和方案状态未在文档中体现，查看文档的人无法了解进度

  - ✅ **解决**：
    - 在文档头部明确标注评审状态和方案状态
    - 在实施计划章节中添加"当前进度"小节，说明方案状态和进度
    - 状态变更时在修改历史中记录
    - 可选：在文档目录前添加状态摘要，快速了解文档状态

- ❌ **问题**：状态定义不清晰，不知道何时使用哪个状态

  - ✅ **解决**：参考规范文档中的状态定义说明，明确每个状态的适用场景和使用时机

## 10. 文档维护

### 10.1 版本管理

#### 版本号更新规则

- ✅ **主版本号（Major）**：重大更新，如架构升级、设计理念变更
  - 需要更新主版本号（v1.0 → v2.0）
  - **需要架构评审**
  - 示例：架构升级、重大设计变更
- ✅ **次版本号（Minor）**：增加功能等不影响架构的改动
  - 需要更新次版本号（v1.0 → v1.1）
  - **需要技术评审**
  - 示例：新增功能模块、扩展设计内容
- ✅ **修订号（Patch）**：问题修复、文档错误修正、格式优化等
  - 需要更新修订号（v1.0 → v1.0.1 → v1.0.2）
  - **不需要评审**，可直接修改
  - 示例：修复文档中的错误、澄清模糊表述、修正技术细节、补充说明、优化格式、更新链接等
  - **重要**：进行修订号更新时，必须复制原文档创建新版本文件，然后在新文件中修改版本号
    - 原文档保留不变（作为历史版本）
    - 新文档文件名包含版本号（如：`myhub-nav-infra-v1.0.1.md`）
    - 在新文档中更新版本号和修改历史

#### 修改记录要求

- ✅ **修改记录**：所有版本更新必须记录修改的地方和修改时间
  - 在文档中明确标注修改章节
  - 记录修改日期（YYYY-MM-DD 格式）
  - 说明修改原因（如：修复错误、澄清说明、补充内容等）
- ✅ 已锁定的文档如需修改，需要提交设计变更申请

### 10.2 文档状态

- 🔒 **已锁定**：设计已确定，不允许随意修改
- 📝 **进行中**：设计正在进行中，可以修改
- ⏸️ **暂停**：设计暂时停止，保留当前状态

### 10.3 相关文档链接

文档应该包含相关文档的链接：

- ✅ 技术调研文档
- ✅ 相关 RFC 文档
- ✅ 官方文档链接
- ✅ 参考实现链接

## 11. 使用指南

### 11.1 编写新文档时

1. **确定文档名称**：使用 kebab-case，包含 `-infra-v` 后缀和版本号（如：`myhub-nav-infra-v1.0.md`）
2. 复制相应的文档模板
3. 按照本规则逐项填写
4. 使用文档完整性检查清单自检
5. 提交评审前确保所有必需项都已完成

### 11.2 评审文档时

1. **确认版本号类型**：
   - 主版本号（Major）：需要架构评审
   - 次版本号（Minor）：需要技术评审
   - 修订号（Patch）：不需要评审
2. 按照本规则逐项检查
3. 重点关注技术选型和架构设计
4. 检查平台兼容性和风险
5. 提供具体的修改建议

### 11.3 更新文档时

#### 修订号更新流程（Patch，不需要评审）

1. **复制原文档**：
   - 复制当前版本的文档文件（如：`myhub-nav-infra-v1.0.md`）
   - 创建新版本文件（如：`myhub-nav-infra-v1.0.1.md`）
   - **重要**：原文档保留不变，作为历史版本
2. **更新版本号**：
   - 更新修订号（v1.0 → v1.0.1）
   - 在新文档的头部信息中更新版本号
3. **更新文件名**：
   - 确保文件名包含 `-infra-v` 后缀和新的版本号（如：`myhub-nav-infra-v1.0.1.md`）
4. **更新"最后更新"日期**：使用 YYYY-MM-DD 格式
5. **记录修改内容**（必需）：
   - 在文档中明确标注修改的章节和位置
   - 记录修改时间（YYYY-MM-DD 格式）
   - 说明修改原因和修改内容
   - 在"修改历史"章节中添加新记录
6. **更新相关文档链接**：如有变更，同步更新链接

#### 次版本号更新流程（Minor，需要技术评审）

1. **复制原文档**或直接修改（根据团队规范）
2. **更新版本号**：更新次版本号（v1.0 → v1.1）
3. **更新文件名**：确保文件名包含 `-infra-v` 后缀和新的版本号
4. **提交技术评审**：需要技术评审通过后才能锁定
5. **记录修改内容**：同上

#### 主版本号更新流程（Major，需要架构评审）

1. **复制原文档**或直接修改（根据团队规范）
2. **更新版本号**：更新主版本号（v1.0 → v2.0）
3. **更新文件名**：确保文件名包含 `-infra-v` 后缀和新的版本号
4. **提交架构评审**：需要架构评审通过后才能锁定
5. **记录修改内容**：同上
